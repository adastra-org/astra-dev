## 1. Qué cambia respecto de M4 (el motivo del bloqueo)

Hasta M4, ejecutar código en el sandbox era una acción del usuario: un clic sobre un bloque que el usuario ve. Con la fase 2, **el modelo puede provocar la ejecución de código sin que el usuario lo lea antes**. El código lo escribe el modelo, y el modelo lee texto no confiable (documentos importados, la pregunta, el historial, resultados anteriores). La superficie nueva es esa: pasa de "código del lector" a "código de un modelo influenciable".

Lo que NO cambia: el sandbox. Esta fase no toca `bootstrap.ts`, `runner.ts`, `lua.worker.ts`, `run.ts`, `protocol.ts`, `wasm-patch.ts` ni `limits.ts`. Usa `runLua` y `lint` tal cual. (Por eso el resultado no trae `returned`: capturar el valor de retorno habría obligado a tocar el bootstrap.) Si la revisión de M4 encuentra un escape del sandbox, esta fase hereda el problema y ahora es alcanzable de forma indirecta, vía el modelo.

Lo que el server hace: **nada con efectos**. Escanea la salida del modelo, corta el stream y reenvía un resultado escapado. No ejecuta código ni toca archivos ni red a pedido de nadie.

## 2. Modelo de amenazas

Actor principal: un usuario malicioso o un documento/pregunta que intenta, a través del modelo, (a) salir del sandbox, (b) colgar o llenar el navegador, (c) manipular al modelo con lo que devuelve la herramienta, (d) ejecutar algo que el usuario no pidió, (e) sacar datos. El impacto de cada caso se acota al navegador del propio usuario: **no hay estado compartido entre usuarios en este camino** (el resultado no se persiste, no se cachea y no se comparte).

## 3. Decisiones que difieren de la letra del pedido (a mirar en la revisión)

1. **El rol `tool` es lógico.** Pedido: "resultado devuelto como mensaje de rol `tool`, escapado". `LlmProvider` no tiene tools nativas ni rol `tool` (DeepSeek y llama.cpp no aceptan `tool` sin `tool_calls`), y la regla de la casa es que el texto del cliente nunca se reproduce como turno real. Entonces el paso viaja como mensaje lógico `tool` en el protocolo (`steps[].result`) y el server lo **renderiza dentro del mensaje de usuario** como `<pasos>…<resultado>` escapado. Un `role: "tool"` real al proveedor no existe.
2. **`returned` no existe** (ver sección 1).
3. **`check` = lint** (luaparse + reglas del sandbox, sin ejecutar). El pedido decía "lint/ejecución de prueba": elegí lint porque ejecutar ya es `ejecutar` y así `check` no suma superficie de ejecución.
4. **`error.type: "syntax"` es una heurística** sobre el mensaje de Lua (`near`, `unfinished string`...). Un `error("... near ...")` del propio código se rotula `syntax`: solo cambia una etiqueta.
5. **La app es solo oscura** (`DESIGN.md`, `color-scheme: dark`): no hay tema claro que verificar.
6. **Citas tras una herramienta**: cada continuación vuelve a recuperar fuentes; el cliente conserva las de la primera ronda para mostrarlas, y si el índice o el decisor local variaran entre rondas, un `[n]` posterior podría apuntar a otra fuente. Con el mismo índice la recuperación es la misma; **no se verificó con un modelo real**.
